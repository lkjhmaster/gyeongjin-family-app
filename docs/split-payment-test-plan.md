# 통합결제 검증 기준 (배포 전 필수)

## 거래 모델
- 부모 요청: `type=split_payment`, `wallet=split`, `status=pending`, `allocations={free,card,minus}`.
- 승인 후 원장 항목: 결제수단별 `type=expense`, `splitPaymentId=부모 요청 ID`.
- 거절은 승인 전 원장 차감 없음.
- 취소는 부모와 연결된 모든 승인 항목을 동일 트랜잭션에서 취소 처리.

## 안전성 필수 조건
1. 서버에서 인증한 사용자와 자녀의 접근 권한 확인.
2. 서버에서 잔액/마이너스 가용 한도 재계산.
3. 부모 요청 상태가 pending인지 확인; 승인 중복 실행은 멱등 처리.
4. 금액은 0 이상 안전한 정수; 합계는 결제 총액과 일치.
5. DB 트랜잭션에서 부모 승인 + 지갑별 차감 + 감사로그를 원자적으로 기록.
6. 취소 시 이미 취소되었는지 확인하고 동일 트랜잭션에서 모든 항목 원복.
7. 서버 응답을 수신한 뒤 UI와 로컬 원장 갱신. 충돌 시 서버 데이터 우선.
8. 결제 1건의 달력 집계는 지갑별 세부 내역과 중복 합산하지 않음.
9. 통합결제에서 발생한 마이너스 채무는 판매자 수령 지갑 정책(카드용돈)에 따라 서버가 `debtOrigin=card`로 자동 기록한다. 자녀 UI에서 출처를 선택하지 않으며 클라이언트가 보낸 출처 값은 신뢰하지 않는다.
10. 기존 개별 거래 및 과거 수동 보정 데이터 불변.

## 검증 시나리오
- 10,000원 = 자유 5,000 + 카드 3,000 + 마이너스 2,000. 마이너스 원거래의 `debtOrigin`은 서버가 `card`로 자동 기록하며 UI 선택란은 없다.
- 합계 불일치, 음수, 소수, 잔액 부족, 마이너스 한도 초과.
- 부모 두 기기 동시 승인, 승인 직후 중복 클릭.
- 승인과 취소 동시 실행, 취소 두 번 실행.
- 서버 통신 오류 중 재시도.
- 달력 10,000원 한 번만 표시; 상세에서 세 지갑 배분 확인.
- 모바일 320px 폭에서 가로 넘침 및 버튼 반응 확인.

## 현재
서버 원자적 API가 연결되기 전까지 `SPLIT_PAYMENT_SERVER_REVIEW_READY=false` 유지. 운영 배포 및 main 병합 금지.
